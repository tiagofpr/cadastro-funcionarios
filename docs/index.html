Anotações do projeto, organizadas por assunto para consulta nos próximos. Atualizado até a tag v0.5.0.

Visão geral

CRUD de funcionários em Java 8 com Hibernate, Servlets e JSP, sem Spring Boot. A ideia era montar na mão o que um framework faz sozinho: mapeamento, camadas, ciclo de requisição e deploy.

Camadas

fluxo
Navegador -> Filters -> Servlet (controller) -> Service -> DAO -> Hibernate -> PostgreSQL
                              |
                              +-> JSP (em WEB-INF/views)

Cada camada só chama a de baixo. O DAO nunca importa nada de service, e o Service nunca importa nada de servlet. Pacotes: controller, service, dao, model, filter e util, todos sob br.com.tiagoribeiro.

Escopo provided

As APIs de Servlet e JSP usam provided: são necessárias para compilar, mas o servidor já as fornece em tempo de execução. Empacotar de novo no .war pode gerar conflito de versão com o que o servidor carrega.

Compilar contra a menor versão de Servlet

O Jetty 9.4 executa Servlet 3.1, e o Tomcat 9 executa 4.0. Se o pom.xml compila contra 4.0.1, o compilador deixa passar recursos que só existem na 4.0 e o erro só aparece em execução (veja a seção de Filters). Compilando contra 3.1.0, o erro aparece na compilação, e o Tomcat 9 continua rodando normalmente.

Surefire e JUnit 5

O Maven 3.8.x vem com um maven-surefire-plugin antigo (2.12.4), que não enxerga testes JUnit 5: o build passa com "Tests run: 0". Fixar uma versão recente resolve:

pom.xml (build)
<build>
    <finalName>cadastro-funcionarios</finalName>
    <plugins>
        <plugin>
            <artifactId>maven-surefire-plugin</artifactId>
            <version>3.2.5</version>
        </plugin>
    </plugins>
</build>

Confira com mvn -v qual Maven está em uso e com mvn test se os testes aparecem na saída.

Hibernate: configuração

O hibernate.cfg.xml guarda o que pode ser público: dialeto, exibição do SQL, comportamento do schema e a lista de mapeamentos. Usuário, senha e URL ficam em outro arquivo (próxima seção).

hibernate.cfg.xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE hibernate-configuration PUBLIC
        "-//Hibernate/Hibernate Configuration DTD 3.0//EN"
        "http://www.hibernate.org/dtd/hibernate-configuration-3.0.dtd">

<hibernate-configuration>
    <session-factory>
        <property name="hibernate.dialect">org.hibernate.dialect.PostgreSQLDialect</property>
        <property name="hibernate.show_sql">true</property>
        <property name="hibernate.format_sql">true</property>
        <property name="hibernate.hbm2ddl.auto">update</property>
        <property name="hibernate.default_schema">cadastro_funcionarios</property>

        <mapping resource="br/com/tiagoribeiro/model/Funcionario.hbm.xml"/>
    </session-factory>
</hibernate-configuration>

hbm2ddl.auto

ValorO que fazUso
validateSó confere se as tabelas batem com o mapeamentoProdução
updateCria e ajusta tabelas sem apagar dadosDesenvolvimento
create, create-dropApaga e recria tudoSó testes descartáveis

Use o PostgreSQLDialect genérico. Nomes como PostgreSQL9Dialect, comuns em tutoriais antigos, não são mais necessários porque o Hibernate detecta a versão do banco.

hibernate.default_schema faz toda tabela sem schema explícito cair em cadastro_funcionarios, sem alterar o .hbm.xml.

Senha de banco nunca vai para um arquivo versionado, porque fica no histórico mesmo depois de apagada. O config.properties fica de fora do Git, e um config.properties.example sem dados reais é versionado como documentação.

.gitignore

logs/
util/HibernateUtil.java
public class HibernateUtil {

    private static final SessionFactory sessionFactory = buildSessionFactory();

    private static SessionFactory buildSessionFactory() {
        try {
            Properties db = loadDbProperties();

            Configuration configuration = new Configuration();
            configuration.configure("hibernate.cfg.xml");

            configuration.setProperty("hibernate.connection.driver_class", db.getProperty("db.driver"));
            configuration.setProperty("hibernate.connection.url", db.getProperty("db.url"));
            configuration.setProperty("hibernate.connection.username", db.getProperty("db.username"));
            configuration.setProperty("hibernate.connection.password", db.getProperty("db.password"));

            return configuration.buildSessionFactory();
        } catch (Exception e) {
            throw new ExceptionInInitializerError("Erro ao inicializar o SessionFactory: " + e);
        }
    }

    private static Properties loadDbProperties() throws IOException {
        Properties props = new Properties();
        try (InputStream in = HibernateUtil.class.getClassLoader().getResourceAsStream("config.properties")) {
            if (in == null) {
                throw new IOException("config.properties nao encontrado em src/main/resources");
            }
            props.load(in);
        }
        return props;
    }

    public static SessionFactory getSessionFactory() {
        return sessionFactory;
    }
}

setProperty sobrescreve por código o que viria do XML. A SessionFactory é criada uma única vez, no carregamento da classe, porque é um objeto caro.

Classe de infraestrutura não é DAO: o HibernateUtil fica em util, não em dao.

Mapeamento em XML

O .hbm.xml diz ao Hibernate qual atributo da classe corresponde a qual coluna da tabela.

Funcionario.hbm.xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE hibernate-mapping PUBLIC
        "-//Hibernate/Hibernate Mapping DTD 3.0//EN"
        "http://www.hibernate.org/dtd/hibernate-mapping-3.0.dtd">

<hibernate-mapping>
    <class name="br.com.tiagoribeiro.model.Funcionario" table="FUNCIONARIO">

        <id name="id" column="ID">
            <generator class="native"/>
        </id>

        <property name="nome" column="NOME" type="string" not-null="true" length="100"/>
        <property name="cargo" column="CARGO" type="string" not-null="true" length="100"/>
        <property name="salario" column="SALARIO" type="big_decimal" not-null="true"/>

    </class>
</hibernate-mapping>
AtributoSignificado
class name, tableClasse Java (nome completo) e tabela do banco
generator class="native"O Hibernate escolhe a estratégia do banco. No PostgreSQL vira uma sequence (hibernate_sequence)
typeTipo do Hibernate (string, big_decimal, ...), que não é nem o tipo Java nem o SQL
lengthTamanho da coluna, equivale a VARCHAR(100)
not-nullGera NOT NULL na coluna

O arquivo fica em src/main/resources, no caminho do pacote com barras: br/com/tiagoribeiro/model/Funcionario.hbm.xml. Se a pasta for criada como br.com.tiagoribeiro.model (uma única pasta com pontos no nome), o Hibernate lança MappingNotFoundException. A IDE exibe os dois jeitos de forma parecida, então a conferência é no disco: find target/classes -name "*.hbm.xml".

PostgreSQL no Docker

Um banco pode ter vários schemas, então um único container serve a vários projetos, cada um no seu schema. Banco é o conjunto todo, schema é uma divisão interna dele.

terminal
docker run --name postgres-dev \
  -e POSTGRES_USER=usuario -e POSTGRES_PASSWORD=senha -e POSTGRES_DB=javadb \
  -p 5432:5432 -d postgres

psql -U usuario -h localhost -d javadb -c "CREATE SCHEMA cadastro_funcionarios AUTHORIZATION usuario;"
psql -U usuario -h localhost -d postgres -c "\l"      # lista os bancos do servidor

A URL JDBC sempre aponta para um banco (jdbc:postgresql://localhost:5432/javadb). O schema é escolhido depois, pelo hibernate.default_schema. O erro database "x" does not exist (SQLState 3D000) fala do banco, mesmo quando o nome informado era o de um schema.

DAO

É o único ponto que conversa com o Hibernate. O resto do sistema chama a interface e não sabe como os dados são gravados.

dao/FuncionarioDAO.java
public interface FuncionarioDAO {
    void salvar(Funcionario funcionario);
    Funcionario buscarPorId(Long id);
    List<Funcionario> listarTodos();
    List<Funcionario> listarPaginado(int primeiroRegistro, int tamanho);
    long contar();
    void atualizar(Funcionario funcionario);
    void deletar(Long id);
}
dao/FuncionarioDAOImpl.java (trechos)
@Override
public void salvar(Funcionario funcionario) {
    Transaction transaction = null;

    try (Session session = HibernateUtil.getSessionFactory().openSession()) {
        transaction = session.beginTransaction();
        session.save(funcionario);
        transaction.commit();
    } catch (Exception e) {
        if (transaction != null) {
            transaction.rollback();
        }
        throw new RuntimeException("Erro ao salvar funcionario: " + e.getMessage(), e);
    }
}

@Override
public Funcionario buscarPorId(Long id) {
    try (Session session = HibernateUtil.getSessionFactory().openSession()) {
        return session.get(Funcionario.class, id);
    }
}
  • Uma Session por operação, aberta e fechada com try-with-resources. É simples e evita conexão esquecida aberta.
  • Só operações que alteram dados abrem Transaction. Leitura não precisa.
  • O if (transaction != null) no catch existe porque a exceção pode acontecer antes de beginTransaction() terminar. Sem a checagem, o rollback geraria um NullPointerException que esconde o erro real.
  • session.update(funcionario) usa o id que já está dentro do objeto para montar o WHERE ID = ?. Por isso o fluxo de edição é buscar, alterar os campos e salvar de volta.
  • HQL usa o nome da classe (FROM Funcionario), não o da tabela.

Service e injeção de dependência

O Service aplica as regras de negócio antes de chegar ao DAO. Todo Servlet fala com ele, nunca direto com o DAO.

service/FuncionarioService.java (trechos)
public class FuncionarioService {

    private static final Logger logger = LoggerFactory.getLogger(FuncionarioService.class);

    private final FuncionarioDAO dao;

    public FuncionarioService() {
        this.dao = new FuncionarioDAOImpl();
    }

    public FuncionarioService(FuncionarioDAO dao) {
        this.dao = dao;
    }

    public void cadastrar(Funcionario funcionario) {
        validar(funcionario);
        dao.salvar(funcionario);
    }

    public Funcionario buscarPorId(Long id) {
        Funcionario funcionario = dao.buscarPorId(id);
        if (funcionario == null) {
            logger.warn("Funcionario inexistente, id: {}", id);
            throw new IllegalArgumentException("Funcionario com id " + id + " nao encontrado.");
        }
        return funcionario;
    }

    public void atualizar(Long id, Funcionario dadosNovos) {
        Funcionario existente = buscarPorId(id);
        existente.setNome(dadosNovos.getNome());
        existente.setCargo(dadosNovos.getCargo());
        existente.setSalario(dadosNovos.getSalario());
        validar(existente);
        dao.atualizar(existente);
    }

    private void validar(Funcionario f) {
        if (f.getNome() == null || f.getNome().trim().isEmpty()) {
            throw new IllegalArgumentException("Nome do funcionario e obrigatorio.");
        }
        if (f.getCargo() == null || f.getCargo().trim().isEmpty()) {
            throw new IllegalArgumentException("Cargo do funcionario e obrigatorio.");
        }
        if (f.getSalario() == null || f.getSalario().compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("Salario deve ser maior que zero.");
        }
    }
}

O segundo construtor recebe o DAO de fora. Isso é injeção de dependência por construtor, o mesmo que o @Autowired do Spring automatiza. Com private final FuncionarioDAO dao = new FuncionarioDAOImpl(); direto na declaração, o @InjectMocks do Mockito não consegue trocar o campo e o teste acaba rodando contra o banco real.

Testes unitários

Testes ficam em src/test/java, espelhando o pacote da classe testada. O Mockito cria um DAO falso, então o teste exercita só a lógica do Service, sem banco.

service/FuncionarioServiceTest.java (trechos)
@ExtendWith(MockitoExtension.class)
class FuncionarioServiceTest {

    @Mock
    private FuncionarioDAO dao;

    @InjectMocks
    private FuncionarioService service;

    @Test
    void deveRejeitarFuncionarioComNomeVazio() {
        Funcionario f = new Funcionario();
        f.setNome("");
        f.setCargo("Analista");
        f.setSalario(new BigDecimal("4000.00"));

        IllegalArgumentException e = assertThrows(
                IllegalArgumentException.class, () -> service.cadastrar(f));

        assertEquals("Nome do funcionario e obrigatorio.", e.getMessage());
        verify(dao, never()).salvar(any());
    }

    @Test
    void deveLancarExcecaoAoBuscarFuncionarioInexistente() {
        when(dao.buscarPorId(99L)).thenReturn(null);

        IllegalArgumentException e = assertThrows(
                IllegalArgumentException.class, () -> service.buscarPorId(99L));

        assertTrue(e.getMessage().contains("99"));
    }
}
Anotação ou métodoFunção
@MockCria a dependência falsa
@InjectMocksCria a classe real e injeta os mocks nela
when(...).thenReturn(...)Define a resposta do mock
verify(dao, times(1)).salvar(x)Confirma que o método foi chamado
assertThrows(...)Confirma que a exceção aconteceu
  • Estrutura de cada teste: preparar os dados, executar a ação, conferir o resultado (Arrange, Act, Assert).
  • O Mockito em modo estrito acusa UnnecessaryStubbingException quando um when nunca é usado. Se ao mesmo tempo aparece SQL do Hibernate no console, o mock não foi injetado e o Service está usando o DAO real.
  • assertEquals na mensagem compara caractere por caractere. Use quando a mensagem é um contrato. Para mensagens internas, contains("99") aguenta pequenas mudanças de redação.

Post/Redirect/Get

Depois de um POST que gravou algo, responda com redirect. Assim, atualizar a página repete só o GET da lista e não reenvia o formulário (o que cadastraria o mesmo funcionário duas vezes). Em caso de erro de validação, use forward de volta ao formulário, para manter o que o usuário digitou e mostrar a mensagem.

controller/SalvarFuncionarioServlet.java (doPost)
Funcionario funcionario = new Funcionario();
funcionario.setNome(request.getParameter("nome"));
funcionario.setCargo(request.getParameter("cargo"));

try {
    funcionario.setSalario(new BigDecimal(request.getParameter("salario")));
    service.cadastrar(funcionario);
    response.sendRedirect(request.getContextPath() + "/funcionarios?sucesso=cadastrado");
} catch (NumberFormatException e) {
    reexibirFormulario(request, response, funcionario, "Salario invalido.");
} catch (IllegalArgumentException e) {
    reexibirFormulario(request, response, funcionario, e.getMessage());
}
  • Tudo o que pode lançar exceção (inclusive Long.parseLong do id) precisa estar dentro do try. Uma conversão fora dele vira erro 500 cru para o usuário.
  • getRequestDispatcher com caminho que começa em / parte da raiz da aplicação. Sem a barra inicial, o caminho é relativo à URL atual e aparece algo como /funcionarios/WEB-INF/....
  • Tudo dentro de WEB-INF é inacessível pela URL. As views ficam lá para só serem alcançadas por forward.
  • Ações que alteram dados são POST, nunca links GET. Um GET pode ser disparado por crawler, pré-carregamento ou clique repetido.

O arquétipo do Maven gera um web.xml declarando Servlet 2.3 (DTD de 1999), anterior à Expression Language. Com essa versão declarada, ${funcionario.nome} aparece como texto literal na página. Troque para Servlet 4.0, na sintaxe XSD mostrada acima, e apague o texto solto "Archetype Created Web Application" que o arquétipo deixa dentro de web-app.

JSTL e Expression Language

listar.jsp (trecho)
<%@ taglib prefix="c" uri="http://java.sun.com/jsp/jstl/core" %>

<c:forEach var="funcionario" items="${pagina.itens}">
    <tr>
        <td>${funcionario.id}</td>
        <td>${funcionario.nome}</td>
    </tr>
</c:forEach>
  • ${funcionario.nome} chama getNome(). O nome usado tem que bater com a chave de request.setAttribute("chave", valor). Um erro de digitação não gera exceção, só deixa a tabela vazia.
  • <c:if> não tem else. Para duas saídas, use <c:choose>, <c:when> e <c:otherwise>.

Mensagem de sucesso depois do redirect

O redirect descarta os atributos do request, então a mensagem viaja na URL e é lida no JSP com param:

Servlet e JSP
// Servlet
response.sendRedirect(request.getContextPath() + "/funcionarios?sucesso=atualizado");

<%-- JSP, antes da tabela e fora de qualquer forEach --%>
<c:if test="${param.sucesso == 'atualizado'}">
    <p class="alerta alerta-sucesso">Funcionário atualizado com sucesso!</p>
</c:if>

Se a mensagem ficar dentro do forEach, ela se repete uma vez por linha da tabela.

Arquivos estáticos

CSS, JS e imagens ficam em src/main/webapp/css/, fora do WEB-INF, porque o navegador precisa baixá-los direto. Referência no JSP, dentro do head:

JSP
<link rel="stylesheet" href="${pageContext.request.contextPath}/css/style.css">

${pageContext.request.contextPath} evita escrever o nome do contexto na mão em cada link.

Formulário único

Cadastro e edição usam o mesmo formulario.jsp. O modo é decidido pela existência do id no objeto.

WEB-INF/views/formulario.jsp (trecho)
<c:set var="editando" value="${not empty funcionario.id}"/>

<h1>${editando ? 'Editar' : 'Cadastrar'} Funcionário</h1>

<form method="post"
      action="${pageContext.request.contextPath}${editando ? '/funcionarios/editar' : '/funcionarios/novo'}">

    <c:if test="${editando}">
        <input type="hidden" name="id" value="${funcionario.id}">
    </c:if>

    ...campos...

    <button type="submit">${editando ? 'Salvar alterações' : 'Salvar'}</button>
</form>
  • c:set guarda o booleano uma vez, para não repetir a condição.
  • cond ? a : b na EL funciona como o ternário do Java.
  • Os dois Servlets passam a encaminhar para formulario.jsp, inclusive no reexibirFormulario. Os JSPs antigos devem ser apagados.
  • Efeito colateral: se o id chegar nulo ao reexibirFormulario da edição, o formulário volta em modo cadastro.

Validação no navegador

Atributos HTML5 evitam uma ida ao servidor por erro óbvio. É só conforto de uso, porque quem usa DevTools ou curl ignora essa camada. A validação que vale continua no Service.

formulario.jsp (campos)

AtributoEfeito

maxlengthRespeita o length da coluna no .hbm.xml

Filters

Um Filter intercepta toda requisição antes do Servlet e a resposta na volta. O que vem antes de chain.doFilter(...) roda na ida, o que vem depois roda na volta.

filter/EncodingFilter.java
public class EncodingFilter implements Filter {

    private static final String ENCODING = "UTF-8";

    @Override
    public void init(FilterConfig filterConfig) throws ServletException {
    }

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        request.setCharacterEncoding(ENCODING);
        response.setCharacterEncoding(ENCODING);

        chain.doFilter(request, response);
    }

    @Override
    public void destroy() {
    }
}
filter/RequestLoggingFilter.java (doFilter)
HttpServletRequest req = (HttpServletRequest) request;
HttpServletResponse resp = (HttpServletResponse) response;

long inicio = System.currentTimeMillis();
try {
    chain.doFilter(request, response);
} finally {
    long duracao = System.currentTimeMillis() - inicio;
    logger.info("{} {} -> {} ({} ms)",
            req.getMethod(), req.getRequestURI(), resp.getStatus(), duracao);
}
WEB-INF/web.xml (filtros)
<filter>
    <filter-name>EncodingFilter</filter-name>
    <filter-class>br.com.tiagoribeiro.filter.EncodingFilter</filter-class>
</filter>
<filter-mapping>
    <filter-name>EncodingFilter</filter-name>
    <url-pattern>/*</url-pattern>
</filter-mapping>

<filter>
    <filter-name>RequestLoggingFilter</filter-name>
    <filter-class>br.com.tiagoribeiro.filter.RequestLoggingFilter</filter-class>
</filter>
<filter-mapping>
    <filter-name>RequestLoggingFilter</filter-name>
    <url-pattern>/*</url-pattern>
</filter-mapping>
  • A ordem dos filter-mapping no web.xml é a ordem de execução. O de encoding precisa ser o primeiro.
  • request.setCharacterEncoding só tem efeito antes da primeira chamada a getParameter. O Tomcat 9 decodifica o corpo do POST como ISO-8859-1 por padrão, então "José" chega como "JosÃ©". O Jetty 9.4 costuma assumir UTF-8 e esconde o problema.
  • Esquecer o chain.doFilter(...) mata a requisição no filtro: a página volta em branco, sem erro.
  • O log não grava parâmetros nem corpo da requisição, para não registrar dados sensíveis.
  • Registros já gravados com acento quebrado não são corrigidos pelo filtro. Só os novos.

init e destroy só são métodos default na API Servlet 4.0. O Jetty 9.4 executa a 3.1, onde eles são abstratos. Um filtro compilado contra 4.0.1 sem esses métodos compila, mas falha na subida com AbstractMethodError ... does not define or inherit an implementation of the resolved method 'abstract void init(javax.servlet.FilterConfig)'. Implemente os dois, mesmo vazios.

Paginação

Em vez de carregar todas as linhas, o banco devolve só a página pedida. Passa por todas as camadas.

dao/FuncionarioDAOImpl.java
@Override
public List<Funcionario> listarPaginado(int primeiroRegistro, int tamanho) {
    try (Session session = HibernateUtil.getSessionFactory().openSession()) {
        return session.createQuery("FROM Funcionario f ORDER BY f.id", Funcionario.class)
                .setFirstResult(primeiroRegistro)
                .setMaxResults(tamanho)
                .list();
    }
}

@Override
public long contar() {
    try (Session session = HibernateUtil.getSessionFactory().openSession()) {
        return session.createQuery("SELECT COUNT(f) FROM Funcionario f", Long.class)
                .uniqueResult();
    }
}

setFirstResult e setMaxResults viram offset e limit no SQL. O ORDER BY é obrigatório na prática: sem ele o banco não garante a ordem, e a mesma linha pode aparecer em duas páginas ou em nenhuma.

util/Pagina.java
public class Pagina<T> {

    private final List<T> itens;
    private final int paginaAtual;
    private final int tamanho;
    private final long totalItens;

    public Pagina(List<T> itens, int paginaAtual, int tamanho, long totalItens) {
        this.itens = itens;
        this.paginaAtual = paginaAtual;
        this.tamanho = tamanho;
        this.totalItens = totalItens;
    }

    public List<T> getItens() { return itens; }
    public int getPaginaAtual() { return paginaAtual; }
    public int getTamanho() { return tamanho; }
    public long getTotalItens() { return totalItens; }

    public int getTotalPaginas() {
        return (int) Math.ceil((double) totalItens / tamanho);
    }

    public boolean isTemAnterior() { return paginaAtual > 1; }
    public boolean isTemProxima() { return paginaAtual < getTotalPaginas(); }
}
service/FuncionarioService.java
public Pagina<Funcionario> listarPaginado(int pagina, int tamanho) {
    if (tamanho < 1) {
        throw new IllegalArgumentException("Tamanho da pagina deve ser maior que zero.");
    }

    long total = dao.contar();
    int totalPaginas = (int) Math.ceil((double) total / tamanho);

    if (pagina < 1) {
        pagina = 1;
    }
    if (totalPaginas > 0 && pagina > totalPaginas) {
        pagina = totalPaginas;
    }

    int primeiroRegistro = (pagina - 1) * tamanho;
    List<Funcionario> itens = dao.listarPaginado(primeiroRegistro, tamanho);

    return new Pagina<>(itens, pagina, tamanho, total);
}

O ajuste do número da página protege de ?pagina=0 e ?pagina=999, e também do caso em que o último item da última página é excluído: sem o ajuste, a tela mostraria uma tabela vazia.

controller/ListarFuncionarioServlet.java (doGet)
int pagina = 1;
try {
    pagina = Integer.parseInt(request.getParameter("pagina"));
} catch (NumberFormatException e) {
    // parametro ausente ou invalido: fica na pagina 1
}

Pagina<Funcionario> resultado = service.listarPaginado(pagina, TAMANHO_PAGINA);
request.setAttribute("pagina", resultado);
listar.jsp (navegação)
<c:if test="${pagina.totalPaginas > 1}">
    <nav class="paginacao">
        <c:if test="${pagina.temAnterior}">
            <a href="${pageContext.request.contextPath}/funcionarios?pagina=${pagina.paginaAtual - 1}">Anterior</a>
        </c:if>

        <c:forEach begin="1" end="${pagina.totalPaginas}" var="p">
            <c:choose>
                <c:when test="${p == pagina.paginaAtual}"><strong>${p}</strong></c:when>
                <c:otherwise>
                    <a href="${pageContext.request.contextPath}/funcionarios?pagina=${p}">${p}</a>
                </c:otherwise>
            </c:choose>
        </c:forEach>

        <c:if test="${pagina.temProxima}">
            <a href="${pageContext.request.contextPath}/funcionarios?pagina=${pagina.paginaAtual + 1}">Próxima</a>
        </c:if>
    </nav>
</c:if>

A EL chama os getters: ${pagina.temProxima} executa isTemProxima(), que calcula o valor em vez de guardá-lo. Para testar com muitos registros, vale um main temporário que chama service.cadastrar em um laço, em vez de inserir ids por SQL, porque assim a sequence do Hibernate continua coerente.

Logging

SLF4J é a interface e o Logback é a implementação. O código só conhece o SLF4J, então trocar o backend depois não mexe nas classes.

src/main/resources/logback.xml
<configuration>

    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>logs/cadastro-funcionarios.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>logs/cadastro-funcionarios.%d{yyyy-MM-dd}.log</fileNamePattern>
            <maxHistory>30</maxHistory>
        </rollingPolicy>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
        <appender-ref ref="FILE"/>
    </root>

</configuration>
uso em qualquer classe
private static final Logger logger = LoggerFactory.getLogger(FuncionarioService.class);

logger.info("Cadastrando funcionario: {}", funcionario.getNome());
logger.warn("Funcionario inexistente, id: {}", id);
  • {} em vez de concatenar com +: se o nível estiver desligado, a string nem é montada.
  • INFO é algo normal e relevante, WARN é algo estranho que o sistema contornou, ERROR é falha real.
  • TimeBasedRollingPolicy cria um arquivo por dia e maxHistory apaga os mais antigos que 30 dias.
  • Os logs vão para logs/, que precisa estar no .gitignore.

O plugin roda direto sobre os arquivos do projeto, sem gerar .war. Mudanças no web.xml pedem reinício completo.

Com scanIntervalSeconds ativo e a IDE recompilando em segundo plano, o Jetty pode reiniciar o contexto no meio de uma requisição. O sintoma é IllegalStateException: Committed no sendRedirect, mesmo com o código certo (a operação até chega a gravar no banco). Rodar por uma configuração de Run/Debug da IDE, ou aumentar o intervalo de scan, resolve.

Tomcat (deploy manual)

terminal
mvn clean package
cp target/cadastro-funcionarios.war /caminho/do/tomcat/webapps/
/caminho/do/tomcat/bin/startup.sh
# http://localhost:8080/cadastro-funcionarios/funcionarios
/caminho/do/tomcat/bin/shutdown.sh
  • O .war é o pacote fechado com classes, JSPs e web.xml. O Tomcat o descompacta sozinho em webapps/.
  • No Tomcat o contexto vem do nome do arquivo (funcionarios-v2.war viria a ser /funcionarios-v2). No plugin do Jetty ele é definido no pom.xml.
  • mvn package também roda os testes, e o build para se algum falhar.
  • Prefira o zip ou tar.gz do Tomcat ao instalador do Windows, que instala como serviço e esconde esses passos.
